| W1 | Workflows are written in `factory/workflows/`, and the copies GitHub runs in `.github/workflows/` are installed from there once the pull request merges. | A pull request that changes `.github/workflows/` runs its changed version, with the repo's secrets, the moment it opens; GitHub runs nothing in `factory/workflows/`. | Applying workflow changes by hand: a change with no ticket. Agents changing `.github/workflows/` directly: it runs before anyone reads it. Installing only on the owner's approval: M272a. | #40, #272 |
| W2 | The installer, `install-workflows.yml`, is a workflow written out in full: it runs one script, by git id (W272b), and takes its credential only to push. | The credential can write workflow files, enough to read every secret, and an agent can change a script while `main` is not locked. | A step in `ship.sh` or `apply-setup.sh`: both are scripts, and their callers would have to pass them the credential. Running no repo script: the rule would be written twice. | #40, #272 |
| W3 | The installer installs a pull request the repo's owner approved at its last commit or merged themselves, and any other only as W272a says. | `ship.sh` starts it, but anything with `actions: write` could, so it trusts nothing about how it was started. | Trusting that `ship.sh` only starts it after an approved merge: anything with `actions: write` can start it. Only what the owner approved: every workflow change waited for them (M272a). | #40, #272 |
| W4 | `ship.sh` starts the installer after a merge that changed `factory/workflows/`. | A merge made with the workflow's own token starts no workflow, so the factory's merges need the explicit start. | A `push` trigger on `main`: the factory's own merges would not fire it, and a bot's direct push would. | #40 |
| W5 | The installer's credential is a GitHub App created for the project, installed on this repo only, allowed to write contents and workflows and nothing else. | A workflow's own token can never write a workflow file; an app commits under its own name, and its tokens last an hour. | A fine-grained personal token: pasted by hand at each expiry, and it acts as the owner. A classic `workflow` token: reaches every repo on the account. | #40 |
| W6 | `workflow-app.sh` refuses an app installed on anything but this one repo, asking the installation's own token which repos it reaches. | The same key would otherwise write those repos' workflows too. | Accepting whatever the owner clicked. Accepting any "Only select repositories" installation: it can hold several. | #40 |
| W7 | `check-inventory.sh` fails when an installed workflow differs from its source, unless the change edits the source and leaves the installed copy alone. | Nobody then edits an installed copy by hand, and an approved change never installed turns `main` red instead of being forgotten. | Failing on any difference: Fred's own workflow pull request could never pass. Comparing only at install time: misses a hand edit. | #40 |
| W8 | The manifest lists only the workflow sources, and `scaffold.sh` makes a new project's `.github/workflows/` from them. | A new project then starts with the two folders matching, and nothing runs in a project that does not exist yet. | Listing both folders: a new project got mismatched folders, and a failing first lint, whenever a change was waiting to be installed. | #40 |
| W9 | The `guard-main` alarm ignores pushes by the project's workflow app (`WORKFLOW_APP_SLUG`). | An alarm on every install would teach the owner to ignore the alarm, and only the installer can get the app's token. | An issue for a person after every installed change: the alarm stops being read. | #40 |
| W10 | The installer installs a file only when its source on `main` is byte for byte what the approved commit held. | A change pushed straight to a source on `main` would otherwise ride in with the next approved pull request touching that file. | Copying whatever `factory/workflows/` holds on `main`: lines nobody approved. | #40 |
| W11 | The installer installs a file only when the installed copy is byte for byte what the pull request's diff was made against. | The diff the owner read is then exactly the difference between what ran before and what runs after. | Installing without that comparison: an old approved pull request could be replayed to bring an old workflow back. | #40 |
| W12 | What is installed is the approved commit's copy of the file, taken from git and not from the checkout, and only an ordinary file. | A copy of the checked-out file would follow a link to contents nobody approved. | Copying the file from the checkout: a link in its place would be followed. | #40 |
| W13 | If any file fails, nothing is installed and the ticket gets `needs-human`; the way back is a ticket restoring the source to what is installed. | A new change on top of `main` would be refused too, because its diff starts from a source that never ran. | Installing a refused change's successor from `main` as it is: lines the owner never saw in one diff. | #40 |
| W14 | The owner merging by hand starts the installer through `pull_request_target`, which runs `main`'s copy and none of the pull request's code. | The owner's own merge raises an event, and without the trigger it would leave `main` failing lint until someone remembered. | Starting the installer by hand after such a merge: `main` red until someone remembers. | #40 |
| W15 | `check-inventory.sh` fails a change to a workflow source that on `main` already differs from its installed copy. | The installer would refuse that change only after it had merged. | Leaving it to the installer: a merge of a change that cannot be installed. | #40 |
