| S287a | A product has accounts unless its `PURPOSE.md` says not, and `sign-in.sh` switches Neon Auth on for it at setup. | Nearly every product has accounts, and Neon Auth keeps users in the database setup already made, so each preview's branch holds its own. | Auth.js: sign-in code for every project to write. Clerk: a second account and free plan. `--meta auth=true` in `database.sh`: nothing for a database that exists. | #287 |
| S287b | `sign-in.sh` sets `NEON_AUTH_BASE_URL` for production only; a preview gets the address of its own database branch from Neon's Vercel integration. | Production's address in a preview would have every pull request's tests sign users up in production, which `ARCHITECTURE.md` (Environments) rules out for the database. | Setting it for preview too, as #287 asked: previews would share production's users. A CI step that sets each preview's address: it needs the Vercel token [M9](setup.md) refuses. | #287 |
| S287c | Production and preview each get a `NEON_AUTH_COOKIE_SECRET` of their own, generated at setup, stored as sensitive, and never printed or held in a variable. | A preview runs unreviewed code that can read its environment, so the secret it holds must sign nothing production accepts. | One secret for both: a preview could forge production's cookies. A copy in GitHub's secrets: nothing in CI reads it. A `FORCE=1` that replaces it: everyone signed out. | #287 |
| S287d | For a product with no accounts, `PURPOSE.md` holds the bullet `- **Have accounts.**`: the purpose skill writes it and `sign-in.sh` reads it. | A script cannot judge prose, and the purpose is the one thing setup asks the owner ([S4](setup.md)). | A flag to `bootstrap.sh`: a command for the human to type. A settings file: a second place saying what the product is. An agent reading `PURPOSE.md`: tokens for a `grep`. | #287 |
| S287e | A run of `sign-in.sh` that fails after Neon Auth is on leaves it on, and the next run carries on from there. | Switching it off could remove a product's users, and auth whose variables are not yet set changes nothing for the app. | Disabling it on failure, as `database-key.sh` revokes its key: a re-run on a live product would risk its users to undo nothing harmful. | #287 |
