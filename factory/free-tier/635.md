### #635. The weekly usage counts are read from production's database

- **Set:** the first step of `measure-initiatives.yml` asks production's database, each Monday, how many times each event happened in each week and how many users did it, with the `NEON_API_KEY` secret and the `NEON_PROJECT_ID` variable (ticket #635; `decisions.md` [M635a](../decisions/635.md)).
- **Protects:** Neon's compute-hours, which this spends.
- **Why:** the factory holds the database's key from setup, so the counts need no secret that a person must store, and the step that holds the key runs before the checkout, so it cannot wait to learn whether an initiative's date has come.
- **Numbers, before:** the job asked the product's address `/api/usage`, which wakes the database as well, and only in a week when a shipped initiative's date had come.
- **Numbers, after:** worked out, not measured: a workflow cannot run before it merges. One wake each Monday. A database woken for one question and left to sleep uses about 0.02 compute-hours ([entry 2](entry-2.md)), so about 0.09 compute-hours a month of the 100 Neon's free plan gives. The job's billed minute is as [entry #631](631.md) says.
- **The event-driven way:** none will do. A date that has come is time passing, which no event marks, and nothing happens in the repository when a user uses the product.
- **Automated:** yes.
