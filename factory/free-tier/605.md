### #605. Production's accounts are counted once for each review and each run of Peta

- **Set:** the first step of the `e2e` job in `ci.yml`, and a step of `refine.yml` once Peta is known to run, ask production's database how many accounts it holds (ticket #605; `decisions.md` [M605a](../decisions/605.md), [M605b](../decisions/605.md)). Adam and Peta are told the number, and no file holds it.
- **Protects:** Neon's compute-hours, which this spends.
- **Why:** Peta sizes an idea's slices, and Adam judges a pull request's weight, by how many people use the product, and a number written down is wrong by the next sign-up.
- **Numbers, before:** nothing in the factory asked production's database a question between merges. Its compute sleeps after 5 idle minutes, and a database woken for one question and left to sleep uses about 0.02 compute-hours ([entry 2](entry-2.md)).
- **Numbers, after:** worked out, not measured: a workflow cannot run before it merges. One wake at most for each push to a pull request that is not a draft, and one for each run of Peta. At the 62 reviews of 19 and 20 November 2026 ([entry #541](541.md)), 31 a day, that is about 930 wakes and 19 compute-hours a month of the 100 Neon's free plan gives, if no two fall within the same 5 minutes and nobody is using the product. Pushes come in bursts and a database a runner is using is already awake, so the real figure is lower. Neon's console shows the month's compute-hours.
- **The event-driven way:** a sign-up is the event that changes the number, and it happens in the product, which tells the factory nothing. Counting then would have the app write to the repository on every sign-up, and #605 names no file of the app.
- **Automated:** yes.
