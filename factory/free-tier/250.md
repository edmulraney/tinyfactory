### #250. Reviews start beside the checks

- **Set:** in `ci.yml` the `adam` and `ryan` jobs need `e2e` alone, and no longer `checks`; `e2e` needs no job, and its first step decides whether its tests run; `fits-main` needs no job; `merge` needs all five to pass (ticket #250; `decisions.md` [A2](../decisions/250.md), [M17](../decisions/57.md), [M75a](../decisions/75.md)).
- **Protects:** the owner's time, at the price of Actions minutes and Claude usage.
- **Why:** the jobs ran in a line, so every run waited for `checks` before a review began, and a review fails far more often than `checks` does.
- **Numbers, before:** 16 clean runs on 17 November 2026 took 9.3 minutes each: `checks` 3.7, the reviews 1.4, `fits-main` 3.5 ([entry #249](249.md)), and 0.7 left for the merge and the gaps between jobs. So `fits-main` ran in all 16, which it did only when a review found that `main` had moved since `checks`. Without it a run took 5.8. Why it ran in every one is not known: the runs could not be read when this was written, and `main` moved 18 times between 08:00 and 11:54 that day (`git log`), once in 13 minutes, which meets a 5-minute wait about one time in three. Of 74 failed runs since 16 November, `checks` failed in 7 and a review in 50.
- **Numbers, after:** worked out, but for how often `main` moves, which was measured: from 17 November 2026 at 12:32 UTC, when this merged, to 18 November at 17:00, 61 pull requests merged and `rerun-fits-main.yml` ran 7 times, so `ship.sh` asked for `fits-main` again in about one clean run in nine.
  - A clean run under which `main` does not move: 4.4 minutes by the clock, `checks` 3.7 and the merge 0.7, against 5.8. The reviews end inside the time `checks` takes, and `fits-main` is skipped and billed nothing.
  - A clean run under which `main` moves, worked out as one in three on a day like 17 November, measured since as one in nine, and none with one ticket in flight: `ship.sh` asks for `fits-main` again, so about 9 minutes by the clock (4.4, then 3.5, the merge again and two starts), against 9.3. It bills 2 minutes more than before, `rerun-fits-main.yml` and the second merge ([entry 10](entry-10.md)): `fits-main` itself was billed either way.
  - A push that changes no app code: 1 billed minute more. `e2e` has to start to ask, where a condition skipped it for nothing ([entry #75](75.md)); 42 of 56 pull requests changed no app code. The reviews begin when it has answered, some seconds after `checks`.
  - A push that changes app code: no minute more. `e2e` starts beside `checks`, not after it, and the reviews follow `e2e` as before.
  - A run in which `checks` fails, about one failed run in ten: both reviews now run in it, about 5 minutes and $2.50 ([entry #160](160.md)), where they were skipped ([entry 5](entry-5.md)). What they find reaches the engineer in the same fix round as the failed check.
  - Rejected, a job of its own that asks before the others start: a billed minute on every push, not on three in four, and every job starting some seconds later.
  - Rejected, `fits-main` beside `checks` on every push, as the ticket asked: both would read `main` in the same seconds and record the same commit, so `ship.sh` would ask again in exactly the same runs. 4 billed minutes a push (3.5 by the clock) that spare nothing, and the run under which `main` moves stays at 9 minutes (`decisions.md` [M17](../decisions/57.md)).
  - Rejected, `fits-main` after the reviews, as before: they now end 1.4 minutes into a run of 4.4, so they would catch one move in three, to spare those 2 billed minutes each time.
- **Automated:** yes.
