### #541. Each verdict is posted from the review job

- **Set:** the `review` job of `ci.yml` posts each verdict, publishes the screenshots and saves each transcript itself, and the `verdicts` job that did so after it is gone (ticket #541; `decisions.md` [A427f](../decisions/427.md)). Each session still starts in a checkout of the base, with the pull request's files outside it and a tool list that only reads (`decisions.md` [A427e](../decisions/427.md)), and no GitHub token is within its reach: the checkout keeps none and the step that starts the sessions is given none (`decisions.md` [A541d](../decisions/541.md)).
- **Protects:** Actions minutes.
- **Why:** each job is billed rounded up to a whole minute, so the second job cost a minute or more on every review.
- **Numbers, before:** in run 44723118291 on pull request #538, on 20 November 2026, the `review` job ran 64 seconds, of which the two sessions took 36, and was billed 2 minutes; the `verdicts` job ran 34 seconds and was billed 1 minute. That is 3 billed minutes for the review.
- **Numbers, after:** estimated, not measured: a workflow cannot run before it merges. Over the 62 reviews of 19 and 20 November 2026, from how long each `adam` and `ryan` job ran, each job rounded up to a whole minute: 268 billed minutes as a job for each reviewer, 208 as a `review` job and a `verdicts` job, and 164 as one job that also posts the verdicts, which is 44 fewer than 208. A review whose two sessions each end within a minute is billed 2 minutes where that run was billed 3. `factory/scripts/minutes.sh <from> <to>` over a later week shows what `review` is billed.
- **What it gives up:** the token of the job the sessions run in writes, as it did before ticket #427, where for one day it only read. The owner chose the base's checkout and the tool list over the second job on 20 November 2026, and on the same day asked for the token to be kept out of a session's reach, since the tool list does not keep a session from reading a file.
- **Automated:** yes.
