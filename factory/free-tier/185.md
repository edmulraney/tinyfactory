### #185. A changed workflow's first run is looked for after a merge, not when a workflow ends

- **Set:** `ship.sh` runs `first-runs.sh` after every merge. No workflow is started by another workflow ending in order to ask whether that was a changed workflow's first run (ticket #185; `decisions.md` [A185b](../decisions/185.md)).
- **Protects:** Actions minutes, and the Claude subscription's usage.
- **Why:** which workflows await a first run is recorded on pull requests, which a job's condition cannot read. A workflow started on every other's end would have to run a job to find out, and every job is billed a whole minute.
- **Numbers, the alternative:** worked out, not measured. One billed minute for each workflow run that ends. A ticket with no fix round ends three at least (`implement`, `ci` for its one push, `guard-main` or `approve-merge` at the merge), so 3 minutes or more beside the 9 it uses now.
- **Numbers, as set:** no job and no minute. With nothing waiting, one call to GitHub in a job that already runs; for each waiting pull request, one more and one for each workflow still to run.
- **What it costs:** one retro for each changed workflow, about $1 to $2 of agent usage and 2 billed minutes ([entry 11](entry-11.md)). Of the 67 pull requests merged up to #200, 24 changed a workflow.
- **What waits:** the retro starts at the first merge after the run, not when the run ends. A factory in which nothing merges starts none; a failed `implement`, `approve-merge`, `install-workflows` or `fix` run still gets its own at once ([entry 11](entry-11.md)).
- **Automated:** yes.
